# lablith

GitLab CI pipelines materialized from a small config: hardened,
digest-pinned `.gitlab-ci.yml` from a few rows in one `.lablith` file.

Read [LLM-DISCLAIMER](docs/LLM-DISCLAIMER.md) first.

lablith is the GitLab counterpart of
[actlith](https://github.com/pr0d1r2/actlith), and both are built on
[pipelith](https://github.com/pr0d1r2/pipelith): the same rows mean the
same CI on both forges. A project that starts on a self-hosted GitLab and
moves to GitHub when it is released keeps its CI declaration: renaming
`.lablith` to `.actlith` and running `actlith gen` is the whole move.

```text
## workflows
id|kind|systems|cache|args
ci|gate|-|my-cachix-cache|-
```

That row becomes `.gitlab-ci.yml` and `.gitlab/ci/ci.yml`: the
[hk](https://hk.jdx.dev) gate on Linux x86, Linux arm and macOS runners,
in the pinned `nixos/nix` image with flakes on and the cachix cache wired
in. Every pipeline lablith writes is hardened the same way, with no
option to turn it off:

- One pipeline per change: merge requests, the default branch, tags,
  schedules and manual runs; a push to a merge request branch does not
  run twice.
- Every image pinned by its multi-arch index digest, the version in a
  comment.
- Only `include: local:`: no remote, project or template includes, no
  `extends:`, no anchors. Every job is written out in full.
- `timeout:` on every job, `interruptible: true` on gate and build jobs,
  a resource group for scheduled bump jobs, and `GIT_DEPTH` by kind.
- The cache is pushed only with the masked, protected `CACHIX_AUTH_TOKEN`
  and never from a merge request coming from a fork.
- Every `script:` entry is one command; longer logic lives in a seeded
  script under `scripts/lablith/`.

Every rendered file validates against GitLab's own CI schema in
lablith's gate, so a change that would break it fails here, not in your
project.

## Status

Early, with no release yet; the interface may still change. The core loop
works, and this repository renders its own GitLab pipeline with it
([`.lablith`](.lablith) renders [`.gitlab-ci.yml`](.gitlab-ci.yml)).

- `lablith gen [--check]`: write each row's file, the root file and the
  scripts its kind runs; `--check` writes nothing and names every stale
  or missing file.
- `lablith check`: `.gitlab-ci.yml` and every file under `.gitlab/ci/`
  is generated by a row or listed as hand-written, with a reason; and
  every row would move to actlith.
- `lablith portable`: name each row, kind or arg actlith could not
  render.
- `lablith detect` and `lablith seed --init`: propose rows from the
  files a repository already has, and write a first `.lablith`.
- `lablith report [--format text|json|md]`: rows, runner tags, image
  pins, every CI/CD variable a row reads, and the pipeline schedules to
  create.
- `lablith pin [--dry-run]`: resolve image tags to index digests through
  the registry's API. It is the only command that uses the network.

Exit status: 0 ok, 1 a finding, 2 usage, unreadable input or a refused
row. Every message names its fix.

## Install

With Rust 1.95 or newer, from this repository:

```sh
cargo install --git https://github.com/pr0d1r2/lablith lablith
```

With nix, run it from the flake, or add `packages.<system>.default` to
your dev shell:

```sh
nix run github:pr0d1r2/lablith -- --help
```

## Quick start

```sh
lablith detect            # rows proposed from your flake.nix and flake.lock
lablith seed --init       # write them to .lablith (never over an existing one)
lablith gen               # write .gitlab-ci.yml and .gitlab/ci/*.yml
lablith check             # every CI file is accounted for
```

Then add `lablith gen --check` and `lablith check` to your gate.
[Integration](docs/INTEGRATION.md) walks through it.
