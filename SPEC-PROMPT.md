lablith

Tool that materializes GitLab CI pipelines from a small config: the GitLab
counterpart of actlith, built on pipelith.

# Problem and goals

GitHub Actions is the fleet's CI for open-source repositories, and actlith
renders it. Unreleased and private projects live on a self-hosted GitLab,
where today almost none of them has a pipeline, and the two that do are
hand-written in unrelated shapes. A project moves from GitLab to GitHub when
it is released, so its CI declaration should move with it unchanged.

Goals:
- one small `.lablith` per repository renders the full GitLab CI
  configuration, deterministically, with every image pinned by digest and
  every hardening default applied
- the same rows mean the same CI on both forges: releasing a project is a
  file rename and `actlith gen`, not a rewrite
- check that the committed pipeline still matches the config (drift gate)
  and that every CI file is declared (totality)
- private projects get the same hk gate on CI that public ones get

# Naming

- Crate, binary and repository: `lablith`. (Git)lab + lith, as actlith is
  act(ions) + lith. Fleet family `pklith`, `actlith`, `pipelith`,
  `microlith`, `xenolith`. `cargo install lablith` gives the `lablith`
  command.
- Availability checked 2026-10-16: `lablith` free on crates.io (API returns
  404); no GitHub repository `pr0d1r2/lablith`. Recount: `curl
  https://crates.io/api/v1/crates/lablith`, `gh repo view pr0d1r2/lablith`.
- "lab" alone may read as laboratory: the README's first line and the crate
  description say "GitLab CI".
- Rejected alternatives (2026-10-16):
  - `glablith`: free, but echoes `glab`, the official GitLab CLI, and
    suggests a link that does not exist.
  - `gitlith`: free, but says git, not GitLab, and would fit a git tool
    better.

# Survey (2026-10-16)

Local checkouts next to this repository, read-only. Recount by listing
`git remote -v` per checkout and `ls */.gitlab-ci.yml`.

- 52 checkouts have a remote on the self-hosted GitLab; 46 of them have no
  GitHub remote at all.
- 2 checkouts have a `.gitlab-ci.yml`. Neither runs the hk gate:
  - one runs lint tools one by one inside `nix develop` on the
    `nixos/nix:latest` image (unpinned tag), in `lint` and `test` stages;
  - one is a Rails application with a Postgres service and GitLab's
    built-in security templates (`include: template:`).
- No checkout renders its GitLab CI from a config.
- The self-hosted instance's runner fleet (executors, tags, architectures)
  is not visible from the checkouts; see open questions.

Conclusion: on GitLab the problem is not drift between copies yet but
absence. lablith lets a private project have the fleet's CI from its first
commit, in the shape it will keep on GitHub.

# Workflow kinds

The kinds, their row values and their intent are pipelith's neutral
catalogue (`pipelith/docs/KINDS.md`). This repository adds
`docs/KINDS-GITLAB.md`: how each kind renders in GitLab CI syntax. v1
renders every neutral kind: `gate`, `build`, `update-pins`, `upstream`.

# Config: `.lablith`

Same grammar as `.actlith` (pipelith `registry`): a `format 1` line,
`## <section>` headings, pipe tables, `#` comments, `-` empty, `\|` literal
pipe. Sketch, not final:

```
format 1

## workflows
id|kind|systems|cache|args
ci|gate|x86_64-linux, aarch64-linux|pr0d1r2|-
update-pins|update-pins|x86_64-linux|pr0d1r2|-

## images
image|version|digest

## runners
system|tags

## hand-written
path|reason
```

- `## workflows` is the neutral section: identical columns and meaning to
  actlith's. A row valid here is valid in `.actlith`.
- `## images` overrides the built-in image pin table, as `.actlith`
  `## actions` overrides action pins. GitLab-only.
- `## runners` overrides the built-in system-to-runner-tags table, since a
  self-hosted fleet chooses its own tags. GitLab-only.
- `## hand-written` as in actlith: files under lablith's layout that are
  not generated, each with a reason.

# Output layout

- `.gitlab-ci.yml` (generated): `workflow: rules`, `stages:`, defaults, and
  one `include: local:` per row and per hand-written file.
- `.gitlab/ci/<id>.yml` (generated): the jobs of one row, all job names
  prefixed with `<id>:` so rows never collide in GitLab's single job
  namespace.
- `scripts/lablith/*.sh` (generated): seeded scripts the kinds call.
- Every generated file starts with `# generated by lablith gen from
  .lablith; do not edit`.

One file per row keeps actlith's one-file-per-workflow diffs and totality
check, despite GitLab having one root file.

# lablith CLI

Verbs mirror actlith's:

lablith gen [--root DIR] [--check] # render .lablith; --check writes nothing, exit 1 naming stale or missing files
lablith check [--root DIR] # totality: root and every file under .gitlab/ci/ generated or hand-written
lablith detect [--root DIR] # proposed rows from tracked files (pipelith detect)
lablith seed --init # first .lablith from detect; never over an existing file
lablith report [--format text|json|md] # rows x systems x image pins, secrets and pipeline schedules each needs
lablith pin [--dry-run] # resolve image tags to digests (network, opt-in)
lablith portable # exit 1 naming each row or key actlith cannot render
lablith completions <shell> · lablith man

- Exit codes as in actlith: 0 ok, 1 finding, 2 usage, unreadable input,
  unknown kind, key or system, newer format.
- No `import` in v1: two hand-written pipelines in the fleet, neither in a
  kind's shape (survey). They become `## hand-written` rows or are
  rewritten as rows by hand.

# Decisions (2026-10-16)

1. Built on pipelith: registry grammar, YAML writer, generated-file set,
   neutral kind catalogue, nix systems and detect rules come from pipelith.
   lablith owns only GitLab: the pipeline model, runner tags, image pins,
   hardening, file layout, scripts and its CLI. Local.
2. Deterministic core as in actlith: same `.lablith` and same lablith
   version give byte-identical files. No LLM, no guess, no clock, no host,
   no network except `lablith pin`. Local.
3. Image pins: every `image:` is `<name>@sha256:<digest>` with the version
   as a trailing comment, from a pin table (built-in, overridable in
   `## images`). `gen` never resolves tags; `pin` queries the image
   registry's HTTP API and writes the table. The fleet's current
   `nixos/nix:latest` is the case this fixes. Local.
4. No remote code: no `include: remote:`, `include: project:`,
   `include: template:` or CI/CD components in generated files, for the
   reasons actlith rejected reusable workflows (trust spans repositories,
   lint sees one line, a fix lands without review). Only `include: local:`.
   A repository that needs a template lists a hand-written file. Local.
5. Hardening defaults in every kind, not optional:
   - `workflow: rules` that run one pipeline per change (merge request
     pipelines, branch pipelines only for the default branch and tags,
     schedules), so a push to an MR branch does not run twice;
   - `timeout:` on every job (default 30 minutes);
   - `interruptible: true` on gate and build jobs, never on scheduled bump
     jobs, which instead take a `resource_group` per row (the GitLab form
     of actlith's never-cancel rule for scheduled kinds);
   - `GIT_DEPTH` set per kind; no job prints or echoes a variable;
   - cache push skipped when the merge request comes from a fork
     (`$CI_MERGE_REQUEST_SOURCE_PROJECT_ID != $CI_PROJECT_ID`);
   - secrets only as masked, protected CI/CD variables; jobs that need
     them run only on protected refs or schedules;
   - every `script:` line is one command; longer logic is a seeded script.
   Local.
6. Schedules are not in GitLab YAML. Scheduled kinds render jobs gated by
   `$CI_PIPELINE_SOURCE == "schedule"` and a selector variable
   `LABLITH_ROW == "<id>"`, so several schedules on one project start only
   their own row. `lablith report` lists each schedule to create (cron,
   branch, variable), the way actlith's report lists secrets. Local.
7. Secrets by purpose, from pipelith's catalogue: `CACHIX_AUTH_TOKEN` for
   cache push; `LABLITH_TOKEN`, a project access token with the smallest
   scope that pushes a branch and opens a merge request, for bump kinds.
   Seeded `scripts/lablith/open-mr.sh` uses the GitLab API through
   `curl`, so no extra CLI joins the dev shell. Local.
8. Output gate, offline: generated files validate against GitLab's
   published CI JSON schema, vendored in `tests/` at a recorded GitLab
   version, with no finding. JSON schema validation and YAML reading are
   test-only dependencies, each with a §R row. There is no zizmor
   counterpart for GitLab; decision 5's rules are §V invariants with a test
   each instead. A server-side `glab ci lint` run is optional and manual,
   never in the gate (it needs network and a token). Local.
9. Portability (pipelith decision 4): `lablith portable` and a check inside
   `lablith check` report every row, system or argument key that actlith
   cannot render. GitLab-only sections (`## images`, `## runners`) are
   ignored by the check, because they do not move. Local.
10. Release migration: a project moving to GitHub renames `.lablith` to
    `.actlith` (subject to pipelith open question 1), runs `actlith gen`,
    and deletes `.gitlab-ci.yml` and `.gitlab/ci/` in the same reviewed
    commit. The release procedure is a page in this repository. Local.
11. Visibility: lablith is public on GitHub from the first push, MIT,
    like the other fleet tools. Its own CI is GitHub Actions rendered by
    actlith. It also commits its own `.lablith` and the rendered GitLab
    files, which its GitLab mirror runs on a real runner. Local.
12. No private names: runner tags, image registries, host names and
    project paths of the self-hosted instance never appear in committed
    files of this repository; built-in defaults use neutral tags (the nix
    system name plus `nix`), and each private repository overrides them in
    its own `.lablith`. Candidate for the paradigm (extends its name
    guard, decision 40).
13. Fleet membership: with lablith, private projects on the self-hosted
    GitLab can have a pipeline, which paradigm decision 45 named as the
    reason to keep them out of the registry. Proposing that change is a
    gap round on the paradigm, not part of this build. Candidate for the
    paradigm.
14. Fleet rollout: dogfood on lablith itself, then private projects one at
    a time, each by `detect`, a reviewed diff and explicit approval, as in
    actlith. Local.

# Non-goals

- No GitLab-only product features in v1: security templates, Auto DevOps,
  environments and deployments, review apps, services such as Postgres.
  A project that needs them lists a hand-written file.
- No kinds that GitHub cannot render (pipelith decision 6).
- No runner provisioning: lablith renders tags; registering runners is the
  instance owner's work.
- No import of existing pipelines in v1.

# Prior art and rejected designs

- GitLab CI/CD components and `include: project:` from a central
  repository: rejected, for the reasons in decision 4.
- One root `.gitlab-ci.yml` holding every row: rejected. It loses
  one-file-per-row diffs and turns totality into a check of YAML keys
  instead of files.
- `extends:` and YAML anchors for shared job parts: rejected in generated
  output. The generator already shares them; expanded jobs read and
  validate on their own, as actlith's expanded steps do.
- Converting GitHub workflows to GitLab (GitLab's migration guides and
  converters): rejected. They translate text once; lablith renders both
  forges from the same rows every time.
- Differentiator: one set of rows, two forges, both deterministic and
  drift-checked, with the move between them made mechanical.

# Open questions

1. Runner fleet of the self-hosted instance: executor (Docker with a
   pinned `nixos/nix` image, or a shell executor on NixOS hosts that needs
   no image), architectures available (`aarch64-linux`? any
   `aarch64-darwin` runner?), and the tags to use as defaults. Blocks the
   runner-table node and the `build` kind; if no macOS runner exists, the
   default `systems` for GitLab differ from GitHub's, and decision 9 must
   say whether that is a portability finding.
2. Nix store cache on GitLab: cachix as on GitHub (same secret, same
   steps), or a cache on the instance itself. Proposed: cachix, so the
   `cache` column means the same on both forges. Blocks the `build` kind.
3. Config file name: pipelith open question 1. Blocks the release
   migration page only.
4. GitLab version of the instance, which fixes the CI JSON schema version
   to vendor (decision 8) and whether `workflow: auto_cancel` is
   available. Blocks the output-gate test node.

# Learnings from actlith and pipelith (2026-10-17)

Written after actlith 0.1.0 shipped and its `main` moved every neutral
part onto pipelith. Treat these as inputs the spec should absorb: where
one contradicts a decision above, the later learning wins unless the spec
says why.

## State of the siblings

- pipelith 0.1.1 is on crates.io (`pipelith = "0.1"`). It is std only.
  actlith 0.1.0 is on crates.io. actlith's `main` takes `registry`,
  `kind`, `system`, `yaml`, `files` and `detect` from pipelith, with
  every golden byte-identical (actlith PRs #7 to #14). Build order steps
  1 and 2 are done; lablith is step 3.
- Depend on pipelith from crates.io, not a git pin. A git dependency
  needs a `deny.toml` allow-git rule and nix `outputHashes`, and it blocks
  publishing, because crates.io refuses crates with git dependencies.

## The pipelith API, as actlith uses it

- One facade node names pipelith: actlith's `src/core` re-exports
  `pipelith::{detect, files, kind, registry, system, yaml}`, and its V51
  forbids `pipelith::` paths anywhere else. Start lablith with the same
  node, first in build order.
- Registry: `registry::parse(FILE, text, &Schema { sections })`. The
  sections are `kind::WORKFLOWS` (neutral) plus the forge's own
  `SectionSpec { name, columns, required, key }`. For lablith those are
  `## images`, `## runners` and `## hand-written`. Rows come back as
  cells; `kind::RawRow::from_cells` types a workflows row, and the
  `registry::{required, optional, list, args}` helpers type the rest.
- Kinds: `kind::{GATE, BUILD, UPDATE_PINS, UPSTREAM}` are `KindSpec {
  name, schema, default_systems, secrets: &[Purpose] }`. actlith's `Kind`
  trait is `spec()` + `secrets()` + `build()`. `Row::check(spec, raw,
  &EXTRAS)` checks systems, cache, args, `timeout` and the row rules:
  cache required for `build`, `package` a plain word, `cron` without
  commas, the shape of `token`, plain words for `build`/`script`/
  `branch-prefix`, and one system for bump kinds. It reports the first
  fault in that order.
- `ArgDefault::Forge` marks a default the forge supplies. `token` is
  `GITHUB_TOKEN` on actlith, and lablith supplies `LABLITH_TOKEN`
  (decision 7). `Purpose::OpenChange` is the merge-request token, and
  `Purpose::CachePush` is `CACHIX_AUTH_TOKEN`.
- `kind::Extras { kinds, keys }` declares forge-only kinds and arg keys.
  actlith's is empty. `kind::portable(&raw, &extras)` returns one
  `Finding` per forge-only kind or key, which is decision 9's check.
  `## images` and `## runners` are sections, not keys, so they are not
  findings.
- Systems: `system::{System, parse_system, ALL, DEFAULT_SYSTEMS,
  ci_system}`. The runner label table is the forge's. actlith keeps its
  own `SystemError`, so the message stays "no GitHub-hosted runner"
  instead of pipelith's "no hosted CI runner on any forge". lablith's
  runner tags come from `## runners` (open question 1).
- YAML: `yaml::document(&dialect, comments, entries)` over `Entry`,
  `Node`, `Value`, `Text` and `Expr`, and `Expr::new(&dialect, inner)`.
  The forge supplies `impl yaml::Dialect` with `expr(inner) ->
  Option<String>` and `escape(lit)`. actlith's `Github` writes `${{
  inner }}` and escapes a literal `${{`. lablith needs a GitLab dialect
  (variables `$NAME`, and an escape for a literal `$` in `script:`). That
  is to decide in the spec, with a test per escape.
- Files: `files::{File, write, check, Stale, header(tool, config)}`.
  `header("lablith", ".lablith")` is the generated header. A `concat!`
  copy, which a `const` needs, gets pinned to it by a test, as actlith's
  script header is.
- Detect: `detect::{detect, row_line, text_with, seed_init_text, header,
  FIRST_ROW}`. Since 0.1.1 a forge writes proposed rows itself.
- Errors: pipelith's `RegistryError` prints `file:line:col: what (fix)`
  and `KindError` prints `line N: what (fix)`. actlith converts both into
  its own shape (`.actlith:N: what` / `  fix: ...`). Decide lablith's
  user-facing shape once, and convert at the facade.

## Behaviour decided on actlith that lablith should match

- `update-pins` is off by default (actlith V50). `detect` and `seed
  --init` write it commented out under a note line, through
  `text_with(rows, proposal)`. lablith's note says "MRs":
  `# off by default: uncomment to get daily nixpkgs-lock bump MRs`.
- The first release is `0.1.0`, not a release candidate. The version
  bump lands through a pull request, and the owner runs `cargo release`
  tag, publish and push from `main`. An agent never publishes.
- A bump kind runs `nix develop --command bash scripts/<tool>/....sh`,
  so the consumer's dev shell must provide the tool. For actlith that
  is a pklith catalog row (pklith issue #70). lablith needs the same
  row, and can join that issue or follow it.
- docs/KINDS.md has a parity test against the code and each kind's
  node spec (actlith T33): kind list in code order, args with key,
  required flag and default, and a §V and §T row per kind. Port it for
  `docs/KINDS-GITLAB.md`.

## Gate: steps actlith needed, with the bug behind each

- `build` (`cargo build --workspace --bins`) runs after clippy, and every
  `cargo run` step depends on it. In the push set, `test` waits for every
  `cargo run` step. Otherwise a cargo step relinks a binary while another
  step starts it, and macOS kills that process with no output (actlith
  B9, then B10 when the first fix missed `nextest --workspace`).
- A guard that evaluates the flake reads it as `git+file://<root>`,
  never `getFlake (toString ./.)`. A bare path copies `target/` while
  cargo rewrites it (actlith B8, red CI on one runner of three).
- Push-only steps: `package` (`cargo package --locked`; the packaged crate
  builds alone), `package-nix` (the flake package built and run on a
  fixture), `deny-advisories` (cargo-deny filters `publish = false`
  members, so a dev crate's dependencies are not checked), and
  `schema-pin` (the vendored `pkl/Config.pkl` is the pinned hk's, with
  `pkl/VENDORED.md`). Commit-time steps: `links` (lychee `--offline`) and
  `no-commit-to-branch main`, the latter in pre-commit only.
- hk 2.7.0: vendor its `Config.pkl`, and set `stage = true` on the `fix`
  hook. Move nix-hk and nixpkgs-lock together, so the cached hk is used.
- Branch protection, from the first push: a PR is required with 0
  approvals and admins included, the three `gate (...)` checks are
  required and strict, and force pushes and deletion are off.

## Process lessons

- clippy runs on all targets at every commit, so a RED commit must
  compile and fail at run time. Land a stub, or a TypeId assertion
  against pipelith's type. tdd-order needs a `test:` commit before any
  `.rs` change in the push range, comment-only ones included.
- The coverage ratchet counts a `const fn` that runs only inside consts
  as uncovered. Write such values as literals.
- Adding a node makes `sherd sync` add a NAV row to every spec, which
  pushes files over their `.context-limits` ceilings. Raise a ceiling to
  about 12% over measured, with the reason in the commit body.
- ctrm keeps `.rs` files ASCII: write `\u{a7}` in strings, never `§`.
  markdownlint MD024 needs `siblings_only`, because the changelog
  repeats `### Added` under every version.
- A commit subject is at most 72 characters.
- Write the human docs from the start: a README introduction that routes
  to docs/INTEGRATION.md, REGISTRY.md, CONTRIBUTING.md, SECURITY.md and
  CODE_OF_CONDUCT.md. Add the crates.io and docs.rs badges only once the
  pages exist.
- A plan agent that maps one crate's modules onto another's API before
  any code moves saved rework. Its "suspected difference" claims were
  checked by a throwaway probe, and one of them, a blank line after a
  section heading, turned out to be false.

# Process

The paradigm lifecycle: dev shell, then ask me to reload; guardrails first,
one check per commit, then ask me to reload; TDD; 1-to-1 unit coverage with
floor and ceiling, aiming at 100%; federated SPEC-DAG built in sherd waves.
Build order with the sibling crates: pipelith first, then actlith switches
to pipelith, then lablith. As of 2026-10-17 the first two are done (pipelith
0.1.1, actlith `main` on pipelith); lablith starts on pipelith 0.1.1.
