# Kinds on GitLab

How lablith renders each kind of pipelith's neutral catalogue
(`docs/KINDS.md` in pipelith) in GitLab CI. A row means the same on both
forges; this page says what GitLab gets for it. The law is the kind
nodes' specs (`src/gate`, `src/build`, `src/bump`); a test keeps this
page, the code and those specs in step.

## Common to every kind

- Every generated file starts with
  `# generated by lablith gen from .lablith; do not edit`.
- `.gitlab-ci.yml` holds only `workflow: rules` (merge requests, the
  default branch, tags, schedules and web runs: one pipeline per
  change), the stages `gate`, `build`, `verify`, `bump`, and one
  `include: local:` per row file and per hand-written file. No remote
  include, no `default:`, no `extends:`, no anchors.
- `.gitlab/ci/<id>.yml` holds a row's jobs, each named `<id>:<job>`.
- Every job runs the pinned `nixos/nix` image (by its multi-arch index
  digest, the version in a comment above), carries its system's runner
  tags (`nix` plus the system name unless `## runners` says otherwise),
  sets `timeout:` from the row, `GIT_DEPTH` by kind and `NIX_CONFIG`
  with flakes on and the row's cache as a substituter.
- Push and merge request jobs are `interruptible: true` and never run on
  a schedule. Bump jobs are not interruptible, take the resource group
  `lablith-<id>`, and run only on a schedule or web run whose
  `LABLITH_ROW` is the row's id, on a protected ref.
- Every `script:` entry is one line; longer logic is a seeded script
  under `scripts/lablith/`.
- Every job's first command is `bash scripts/lablith/runner-system.sh
  <system>`, so a runner registered with the wrong tags fails before it
  builds, gates or pushes anything. The job's system passes when it is
  the runner's nix `system` setting (`nix config show system`, what
  builds run for; `builtins.currentSystem` would follow `eval-system`),
  or when the runner's nix lists it in `extra-platforms` (`nix config
  show extra-platforms`, asked only when `system` does not match). An
  x86_64-linux NixOS host with binfmt therefore runs `aarch64-linux`
  jobs once `boot.binfmt.emulatedSystems` puts that system there, and a
  Mac whose nix lists `x86_64-darwin` runs Intel jobs under Rosetta.
  That list is the owner's own nix config, so it is trusted as given.
  Otherwise the job stops with `runner nix system is <native>
  (extra-platforms: <list or none>), this job needs <system>`.
- The check needs nix 2.20 or later, which brought `nix config show`.
  A shell executor runs the host's nix, so a shell runner's host needs
  nix 2.20 or later; an older one stops every job with `the runner's
  nix is <version>; this check needs nix 2.20 or later`.
- With the Docker executor the check reads the nix configuration inside
  the pinned `nixos/nix` image, not the host's, so a host's binfmt setup
  (`boot.binfmt.emulatedSystems`) does not reach it and an emulated
  system is refused there. Each job sets its own `NIX_CONFIG`, which
  replaces one from the runner's `environment`, so that is no way in.
  Set `system` or `extra-platforms` in the container's nix configuration
  instead: every job runs the pinned `nixos/nix` image, so mount a
  `nix.conf` that lists them over `/etc/nix/nix.conf` through the
  runner's Docker `volumes`. The job's `NIX_CONFIG` names neither
  setting, so the file's values stand.
- A cache push to the built-in cache goes through
  `scripts/lablith/cachix.sh`, which pushes only when `CACHIX_AUTH_TOKEN`
  (masked, protected) is set and the pipeline is not a merge request
  from a fork.
- A `## caches` cache ([REGISTRY.md](REGISTRY.md)) is read and pushed by
  its row:
  - Reading, url and key literal: both join the job's `NIX_CONFIG` as
    `extra-substituters` and `extra-trusted-public-keys`.
  - Reading, either a secret: neither is in `NIX_CONFIG`. Right after the
    runner check the job runs
    `NIX_CONFIG="$NIX_CONFIG$(bash scripts/lablith/cache-read.sh <url> <key>)"`,
    each argument a literal or `secret:NAME`. The script prints both
    settings only when both values are there, so a pipeline that cannot
    see protected variables runs without the cache, never with an empty
    substituter. The line assigns rather than exports: `NIX_CONFIG` is
    already an exported job variable, and `export` would hide the
    script's exit status, so a refusal would not stop the job.
  - Reading with a netrc (`read=secret:R`): the same line passes `R` and
    the cache's name after the url and key, whether those are literals
    or secrets. When `R` is set, the script checks that the resolved url
    is `https://` and that the netrc has no `default` entry, which
    would reach every host nix talks to; otherwise it stops the job
    naming the cache and `R`, never the url or the credential, before
    it changes the netrc or hands it to nix. It refuses any token
    `default`, in any case and wherever it stands, a password or a
    comment word included, rather than follow curl's grammar; a quoted
    token is read whole. It also refuses a netrc it cannot read. Use
    `machine <cache host>` entries only. Then
    it makes the file
    `R` points at, which the runner writes in the job's temporary
    directory and removes when the job ends, 0600, and prints
    `netrc-file = <file>` after both settings; nix reads the cache with
    it. It makes no copy, so no credential is left on a shared runner.
    Without `R` (an unprotected ref) it prints nothing and the job runs
    without the cache; a fork's merge request never gets that far, as
    the fork guard skips the job. The push below keeps its own netrc.
  - What nix does with the netrc afterwards is nix's, and lablith cannot
    check it. Nix fetches each NAR from the `URL:` of its narinfo, and
    an absolute `http://` one on the cache's host would carry the
    credential in cleartext, so the cache must serve relative or
    `https://` NAR urls, and every redirect it answers with, which nix
    follows with the netrc, must stay on `https://` too. On a multi-user nix (a shell runner whose host
    runs the nix daemon) the daemon substitutes, and it ignores
    `netrc-file` and `extra-substituters` from a client it does not
    trust, so the job runs without the cache: add the runner user to
    the host's `trusted-users`, or set the cache and its netrc in the
    host's own `nix.conf`. The pinned `nixos/nix` image of the Docker
    executor runs single-user nix, where the job's settings apply.
  - Pushing, `push` is `-`: no push step. pipelith refuses a `build` row
    on a read-only cache.
  - Pushing, `secret:NAME`: the command runs through
    `scripts/lablith/cache-push.sh <kind> <cache> NAME <any|default> <command> [installable]`.
    It pushes only when `NAME` and the url are set, the pipeline is not
    a merge request from a fork and, for `build` (`default`), the ref is
    the default branch; otherwise the command runs alone. A cachix
    cache runs the command under `cachix watch-exec` with `NAME` as the
    token. An https cache first checks the flake has the installable,
    `gate`'s `.#devShells.<system>.default.inputDerivation` (everything
    `nix develop` needs) or `build`'s package, and stops naming it when
    it does not; then, with `umask 077`, it copies the netrc file `NAME`
    points at to a 0600 file it removes on exit and runs
    `nix copy --option netrc-file <file> --to <url> <installable>`
    before the command, so a gate's inputs are pushed even when the gate
    fails. It never prints the url; the endpoint must accept
    authenticated `PUT`. A resolved url that is not `https://` is refused
    before the netrc is touched. The push is best-effort: a failed copy is
    a warning and the command still runs and sets the job's status, so a
    push never fails a `gate`; for `build`, `<id>:verify-cache` fails when
    the cache lacks a path.
  - Signing: `nix copy` uploads paths as built, unsigned. Readers trust
    the row's `key`, and nix refuses an unsigned path from a cache it
    trusts by key, so the paths an https cache serves must be signed:
    by the cache when it serves them, or upstream before they are
    pushed. lablith has no signing-key column.
- Every generated job's first rule is
  `if: $CI_MERGE_REQUEST_SOURCE_PROJECT_ID != $CI_MERGE_REQUEST_PROJECT_ID`
  with `when: never`. No generated job runs for a merge request from a
  fork, whether that pipeline runs in the fork or in the parent project,
  and there is no switch to allow it. The root `workflow:` still admits
  merge request pipelines, so a job in a `## hand-written` file runs for
  a fork's merge request unless it carries the same rule itself. On a
  self-hosted GitLab every runner a job's tags reach is the owner's,
  built-in tags included.
- Tags are not an ownership boundary: they only choose among the runners
  the project can already use, and instance or group runners with
  matching tags run these jobs too. Make sure of one of: the runners are
  project runners locked to this project; jobs on them run only for
  protected refs, on runners set to run only protected refs; or every
  instance and group runner with matching tags is one you trust.
- With only generated jobs, a fork's merge request therefore gets no
  pipeline, and with **Pipelines must succeed** on, GitLab blocks its
  merge: a merge request with no pipeline cannot merge. Running its
  pipeline in the parent project does not help, since the guard
  excludes the generated jobs there too. To merge it, a maintainer
  pushes the fork's branch to this project and merges that branch's
  merge request, whose pipeline runs as usual. An unguarded job in a
  `## hand-written` file still joins a fork's merge request pipeline,
  which then runs that job alone and decides the merge check by it.

## `gate`

The hk gate on every supported system.

- Jobs: `<id>:gate:<system>` per system, stage `gate`, `GIT_DEPTH: 0`.
- Script: the row's command, through `cachix.sh <cache>` for the
  built-in cache or `cache-push.sh ... any ...` for a `## caches` push
  secret, pushing the dev shell's inputs to an https cache first.
- args: `command` (default `nix develop --command hk check --all --check`),
  `timeout` (job minutes, default `30`).

## `build`

Build and cache a flake package on every system, then prove the cache
has it.

- Jobs: `<id>:build:<system>` per system (`nix build` of
  `.#packages.<system>.<package>` through `cachix.sh`, or
  `cache-push.sh ... default ...` for a `## caches` push secret, which
  pushes from the default branch only), `<id>:check`
  (`nix flake check --all-systems`, then an eval of the package on every
  system without runner tags), and `<id>:verify-cache` on the verify
  stage, needing every build, on the default branch only: through
  `verify-cache.sh` for cachix, or `https-verify.sh`, which asks
  `<url>/<hash>.narinfo` with the read netrc, else the push netrc, for
  an https cache.
- args: `package` (required), `timeout` (job minutes, default `30`).

## `update-pins`

Follow `nixpkgs-lock` and propose the bump as a merge request.

- Job: `<id>:update-pins`, stage `bump`, `GIT_DEPTH: 0`, running
  `scripts/lablith/update-pins.sh <build>` inside the dev shell: update
  the input, build, `lablith pin`, `lablith gen`, then `open-mr.sh`
  pushes `pins/nixpkgs-<short rev>` and opens the merge request through
  the GitLab API; idempotent when the branch exists.
- The schedule lives in GitLab, not in YAML: `lablith report` names the
  cron and the `LABLITH_ROW` variable to give it.
- args: `cron` (default `50 6 * * *`), `build` (default `.#default`),
  `token` (default `LABLITH_TOKEN`: GitLab's job token cannot open a
  merge request, so a project access token stands in),
  `timeout` (job minutes, default `30`).

## `upstream`

Poll an upstream release and propose the bump as a merge request.

- Job: `<id>:upstream`, as `update-pins`, running
  `scripts/lablith/upstream.sh <script> <branch-prefix>`: the
  repository's bump script prints `NEW_VERSION=<version>`, and the
  branch is the prefix and the version.
- args: `script` (required), `cron` (default `20 6 * * *`),
  `branch-prefix` (default `upstream/`),
  `token` (default `LABLITH_TOKEN`, as in `update-pins`),
  `timeout` (job minutes, default `30`).

## Not in v1

GitLab-only features (security templates, Auto DevOps, environments,
review apps, services) are not rendered. A project that needs one lists
its file under `## hand-written`.
